# 2026-08-21 — Eight items from the user's run, and the two that were never asked

**Branch:** `fix/call-mic-permission-and-close-button`. A list of eight complaints from a real
device session. Six had a cause findable in the code, one turned out to be two separate bugs
wearing the same coat, and one is still unproven and needs hardware to settle.

**Deployed to production the same day:** `nowli-ai` and `nowli-backend`, commit `7377ae8`.
Both rebuilt and verified running the new code; no migrations were involved. The Flutter
changes are **not** in that deploy — they need an APK.

---

## 1. Notifications never arrive — the permission sat behind a toggle

The whole notification feature was gated on a checkbox nobody had to tick.
`CallReminderService.requestPermissions()` had exactly one call site in the app:
`create_quests_default.dart`, **inside `if (quest != null && enableCall)`**. From Android 13
`POST_NOTIFICATIONS` is a runtime grant, so a user who never turned "Enable call" on was never
asked — and `sync()` opened with

```dart
if (!await Permission.notification.isGranted) return;
```

which returns in silence. No prompt, no error, nothing in the log. And it is not only call
reminders: `sync()` also arms every **quest alarm**, so a phone full of timed quests rang for
nothing and gave the user no way to find out why.

Two changes. `sync()` now asks instead of giving up — `_ensureNotificationPermission()`,
which requests at most once per app run and returns immediately when the OS has already
recorded a permanent no (cheap on every sync, and a refusal stays refused). And the
create-quest screen asks for **every** quest, not only ones with a call, because a quest with
a time carries an alarm too.

**For the device test:** an account that has already denied twice will not see the dialog
again — Android stops showing it. That one has to be granted in system settings.

## 2. "Nowlii will call you 10 minutes before" — it was five

The home tutorial card and the quest-suggestion card both promised ten minutes.
`CallReminderService._leadMinutes` has been `5`. The copy was written by hand and drifted.

The constant is public now (`CallReminderService.leadMinutes`) and all three places that
quote it — both cards and the create-quest snackbar — read it, so it cannot drift again.

## 3. AI suggested quests — a route that never existed, on the wrong clock

Two independent faults.

`quest_suggestion_service.dart` asked `GET {baseUrl}/api/v1/quests/suggestions`. There has
never been such a route on the Django side, and the request carried **no `Authorization`
header** either, so it would have been a 401 even at the right address. Every response was a
404, the screen caught the null and drew its empty state. Suggestions come from
`/api/insights/` — the AI writes the week's reflections and its quest suggestions in one pass
and caches them together — so that is where it points now, with the token and the same 402
handling `InsightsService` uses.

The second fault reaches the screen users actually see (`ShuffleScreen`, which already called
`InsightsService` correctly). The backend picked suggestions on the **server's UTC clock**:

```python
now = timezone.now()
current_time = now.strftime("%H:%M")
day_of_week  = now.strftime("%A")
```

Both values go straight into the AI prompt *and* into the static fallback's time-of-day
bucket. A user at +02:00 opening the screen at 21:00 was handed morning suggestions at
morning times, and the wrong weekday either side of midnight. Both now read the zone the
phone reported, as does `ref` — the reference date the whole week window and the cache key
hang off. Same rule that has already bitten call reminders and the daily spark reset;
`Apps/users/timezones.py` exists precisely for it.

## 4. The companion's name, on screen and in the call

Two halves of one complaint.

**On screen**, nine places addressed the companion by the product's name — or, twice, by
"Fuzzy", the default written straight into the copy — instead of the name the user gave it:
the call reminder notification title, the call button on Today, both out-of-sparks slots, the
two voice-check popups, and three strings under AI Personalization. They read
`CompanionAvatar.current.name` now, which is hydrated on every profile read and is
synchronous, so no screen has to fetch anything.

**In the call**, the model would address the user by its own name, or answer as though it
were them. Nothing in the persona had ever said the two roles are fixed. It does now, with an
instruction to use the user's name sparingly rather than in every reply.

## 5. "I didn't quite catch your mood" → neutral

The user's rule, and it is the right one: when the model cannot read the mood, **report the
mood as neutral**. A mood that registers as nothing in particular *is* neutral, so this is not
a fabrication — while "I couldn't catch it" was the one tile that read as the app being
broken.

Three paths had to agree, or the wording would depend on which layer failed: the summary
endpoint's empty-field case, `_SUMMARY_FALLBACKS` (the whole GPT call failing), and the
Flutter screen's own fallback when there is no summary object at all. All three say the same
sentence now, in all three languages, and `moodIconAsset` already maps the word "neutral" onto
the peaceful face. Topic and energy still own their misses — inventing those would not be
harmless.

## 6 & 7. The acknowledgement tic — and it was our own instruction

The user reported the companion "always repeating *ah, I understand you*", and separately that
it was "unpredictable". Asked which, the two turned out to be the same complaint.

The cause was one line of the persona:

> Reflect back what you actually hear before responding, so {user_name} feels understood.

Read literally — which is how a model reads it — that says *acknowledge every sentence*. It now
says to respond to what was actually said and reflect it back only where it carries weight,
backed by explicit rules: no stock opener, never two replies in a row starting the same way, no
recurring catchphrase ("small steps"), and no slipping into another language for one.

**Worth watching on the phone:** this is a strict instruction. If the companion now reads as
curt, the dial to turn is "at most one such acknowledgement in an entire conversation".

## 8. The male voice — two real bugs, and the original still unproven

Reported as: the setting saves, but the call still sounds female.

What was **not** wrong: the deployed `nowli-ai` container carries the gender code
(`_resolve_realtime_voice`, `cedar` / `marin`), and the chain profile → `session/new` →
`realtime/token` is correct in the source. Checked by reading the file inside the running
container rather than assuming the deploy was current.

What was wrong, twice:

- **The selector always opened on "Female"** — `_selectedVoice` was initialised to a literal
  and never read the profile. So a user who had picked Male was shown, every time they looked,
  that they had not. There was no way to tell a setting that had failed to save from one that
  had saved fine.
- **The backend save was fire-and-forget**, its failure swallowed as "best-effort; local cache
  already set". That is not cosmetic: the cache is refreshed from the server on later loads, so
  a choice that only ever landed locally silently reverts — and the call goes back to the old
  voice, which is exactly the reported symptom.

Both fixed; the row shows the current value and a failed save says so. **Whether either was
*the* cause is still unproven** — it needs a device. Two log lines settle it in one call:
`Companion voice from profile:` (what the phone sent) and `Realtime voice for this call:`
(what the server granted — `cedar` male, `marin` female).
