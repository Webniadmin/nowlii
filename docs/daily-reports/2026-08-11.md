# 2026-08-11 — Responsive text, and the companion follows the user's pick

**Branch:** `feat/design-implementation`. **Nothing was committed today** — 25 modified files
and 3 new ones sit in the working tree for review. No deploy; the backend was not touched.

Two pieces of work, both requested together: stop text breaking the layout on narrow phones,
and make the chosen companion appear everywhere instead of a fixed orange character.

---

## 1. Text scaling — one lever instead of 900 edits

**The problem with the obvious fix.** Only ~27 of ~930 font sizes in the app use `.sp`; the
other ~900 are raw literals spread over 118 files. Rewriting them was not a safe day's work.
`MediaQuery.textScaler` reaches every `Text` regardless of how its size was written, so one
override at the root does the whole app.

**New:** `lib/core/responsive/responsive_text.dart`, wired into **`MaterialApp.router`'s own
`builder:`** in `main.dart`. It has to hang there and not off `ScreenUtilInit` — the app
inserts a fresh `MediaQuery` from the view, so an override placed above it is discarded.

Behaviour: 375pt and up is untouched; below that type shrinks in proportion to a floor of
0.85 at 320. The OS font-size slider, previously unbounded, is clamped to 0.85–1.15.

### The part that would have been a silent accessibility regression

The first version computed one factor and applied `TextScaler.linear(fit * factor)`. Testing
on the emulator at `font_scale=1.3` reported `userScale=1.0`, which was wrong — **since
Android 14 the platform text scaler is non-linear**: body text grows with the accessibility
slider while headings deliberately stay put. Sampling that curve at a heading size returns
~1.0, so the naive factor would have applied *no enlargement anywhere* — worse than before
the change, for exactly the users who need it.

Rewritten to clamp the platform scaler (keeping its curve) and multiply by the width fit
through a small `_FittedTextScaler`. Measured on the device afterwards:

| | body 14 | heading 32 |
|---|---|---|
| 320dp, OS font 1.0 | 11.95 (×0.853) | 27.31 (×0.853) |
| 411dp, OS font 1.0 | 14.00 | 32.00 |
| 411dp, OS font 1.3 | **16.10** (×1.15, capped) | **32.00** (untouched) |
| 320dp, OS font 1.3 | 13.74 | 27.31 |

The third row is the point: the curve survives, and the width fit composes with it.
Width factors verified at 320 → 0.853, 360 → 0.96, 375 → 1.000, 411 → 1.000.

### Hotspot pass

Scaling text does not move fixed paddings, `SizedBox` widths or hard container heights, and
it does not save a `Text` in a `Row` with no `Flexible` — that overflows rather than wraps.
Fixed: the home greeting; the today's-quest card (a hard `width: 190` that is only correct at
375, so on a 320 the title ran under the illustration — now it reserves the illustration's
column); `Add quest`; the bottom nav (tabs are now `Expanded`, which is what the indicator at
`width/3` already assumed, and their labels go through `.tr` so a longer translation used to
push neighbours off-screen); the shared CTA button; two labels in `today.dart`; and
`task_card.dart`, which had no `maxLines` anywhere.

### A regression that only running it could catch

The first greeting fix used `Flexible` in front of the existing `Spacer()`. Both are flex-1
children, so the row split the free space evenly and the name was clipped to **"HI P…"** with
half the row standing empty. `Expanded` with the `Spacer` removed is the correct shape; the
same mistake was made and fixed in `task_card.dart`. `flutter analyze` cannot see this — it
took a screenshot.

## 2. The companion now follows the user's pick

**The plumbing was already fine and is unchanged:** the pick is `Profile.predefined_option`,
the backend copies that option's picture to `Profile.avatar_logo` (an S3 URL) on save, and the
profile is already cached locally. No new request was added.

**New:** `lib/services/companion_avatar.dart` (identity + a `ValueNotifier`) and
`lib/widget/nowlii_avatar.dart` (`NowliiAvatar(size:)`). Resolution order: cached S3 URL →
bundled `A.png`–`F.png` by option id → default.

State is hydrated **inside `StorageService`'s profile read / write / clear** — the one place
every profile passes through — so no screen has to remember to refresh it, and signing out
drops the previous user's companion. 17 call sites across 14 files now use the widget.

**Bug found on the way:** `ProfileModel.toJson()` read `predefined_option` but never wrote it,
so the cached profile came back with no companion id — which is the offline fallback for every
avatar in the app. Safe to add: that method only feeds SharedPreferences and debug prints.

**Two live bugs fixed:** `edit_profile.dart` and `edit_name.dart` fell back to a hardcoded
`A.png` when an image failed to load, showing every user milo — on the screen where they had
just picked someone else.

**Deliberately not converted:** `Assets.svgIcons.avatar` in `popup_screen.dart` (a stock photo
of a person, not a companion), `upscalemedia-transformed.png` in `ai_call_remiender.dart` (a
page background), and everything in `lib/experimental/` (unrouted).

### Three corrections after review

1. **The swipe-to-talk knob was reverted.** It was not asked for; it is a control, not a place
   the companion is displayed.
2. **The call screen was wrong.** `callStarted.png` is a 240px disc with a *small* character
   inside it, so swapping the whole asset for the avatar blew the character up to fill the
   disc — and it pulsed. The disc is now rebuilt from `popupSpeking` (the same art with no
   character baked in), the companion sits inside at 96, and **only the disc pulses**.
3. **The companion was being cropped.** `BoxFit.cover` plus a circle clip sliced the
   character's feet off. The art the backend serves is **transparent** and needs neither; the
   clip exists only for the bundled `A.png`–`F.png`, which are picker tiles with an opaque
   colour baked in (five of six — only fizzy/E is transparent). The two are now separate
   paths: served art is drawn whole with `contain` and no clip.

**And a mistake worth not repeating:** converting a slot means replacing the *picture*, not the
*footprint*. Sizing the out-of-sparks companion as a 95 square instead of the original 78.885
pushed it 16pt into a text column capped at 200 and it ran over the words. Both sparks screens
were reset to their original widths (79 and 60) and all 17 sites were re-checked against the
dimensions they replaced.

**Consequence to decide on:** two slots (`all_quests_done_popup`, `missed_talks_popup`) were
app-icon-style tiles — the character on an indigo rounded square. With transparent art and no
clip, the tile no longer shows; only the character does. Restoring it is one line per site.

## 3. Verification setup, and a false alarm

The only emulator available is 411dp, so it was driven to exactly **320.0dp** with
`adb shell wm size 840x1867` at density 420 (`wm size reset` restores it). Other widths:
`945x2100` = 360dp, `984x2187` = 375dp.

**"Continue with Google returns 401" was not a bug.** The emulator's clock was **6 days
behind** with `auto_time=0`, so Play Services judged a cached ID token still fresh by its own
wrong clock and handed back one minted on 2026-08-05 that had expired 143 hours earlier. The
backend rejected it correctly (`{"error":"Invalid Google token."}`). Decoding the token showed
`aud` matching the configured client id and `exp` long past. Fixed with
`adb shell settings put global auto_time 1`; sign-in then worked first try. **Check the clock
before suspecting auth** — this is the second time clock skew on this machine has looked like
a credentials problem.

**Both of today's sparks are gone**, one to an accidental call started by a swipe gesture while
scrolling the home screen. The call screen therefore has **not** been visually confirmed; the
uncropped rendering it relies on is proven on the home screen, which uses the same path.
